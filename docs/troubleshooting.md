# Диагностика и восстановление

Безопасные шаги при типовых проблемах. Секреты (`password`, VK-токен) в логах и
статусе маскируются; не публикуйте вывод, если сами добавили в него токен.

## Типовые симптомы

| Симптом | Возможная причина | Безопасная проверка | Действие |
|---|---|---|---|
| В статусе/логе `API 5: User authorization failed` | VK отклонил авторизацию: токен недействителен, истёк/отозван, скопирован от другого аккаунта/приложения, либо в поле не токен | `csqtt status` → `last_error`; проверьте поле **«Токен доступа VK»** | Получите новый токен или используйте режим `vkcalls` с VK-хешами. Убедитесь, что в поле вставлен токен/redirect-URL, а не ссылка сервера |
| Служба «не запущена» | `main.enabled='0'` или автозапуск не включён | `uci get csqtt.main.enabled`; `ls /etc/rc.d/*csqtt*` | `uci set csqtt.main.enabled='1'; uci commit csqtt; /etc/init.d/csqtt enable; /etc/init.d/csqtt start` |
| Профиль выключен, соединения нет | `server.<id>.enabled='0'` | `uci show csqtt` | Включите профиль в LuCI («Профили») или `uci set csqtt.<id>.enabled='1'; uci commit csqtt` |
| Нет интерфейса `csqtt0` | Служба не запущена, профиль не подключился, либо не загружен модуль TUN | `ip link show csqtt0`; `csqtt doctor` | Устраните причину по `doctor`; при необходимости `modprobe tun` и перезапустите службу |
| `FATAL_HANDSHAKE` / handshake timeout | Неверный пароль подключения или несовместимость с сервером | `csqtt doctor`; сверьте `peer` и `password` со ссылкой | Импортируйте ссылку заново; проверьте, что сервер доступен |
| Соединение активно, но трафика нет | Пользовательский прокси не привязан к `csqtt0`; интернет идёт мимо туннеля | `curl --interface csqtt0 …` (см. ниже) | Настройте Mihomo/ssclash на `interface-name: csqtt0` |
| Периодические тайм-ауты при активном соединении | `obfs`/`workers` не подходят серверу или каналу | `csqtt status` (`state=active`, счётчики растут, но отдельные запросы висят) | Подберите `obfs` (`audio`/`video`) и `workers` по рекомендации владельца сервера |
| `doctor` показывает `peer-reachability: warn` | Сервер не отвечает на пробу, но соединение может работать | Сравните с рабочим подключением; перепроверьте `peer` | Если и соединения нет — проверьте адрес/порт и firewall у сервера |
| `rp_filter=1` на `csqtt0` режет обратный трафик | Строгий режим ядра | `cat /proc/sys/net/ipv4/conf/csqtt0/rp_filter` | `sysctl -w net.ipv4.conf.csqtt0.rp_filter=2` (настройка системы, не службы) |
| Активная проверка доступа — «не применима» | Имя цели разрешилось в служебный/синтетический адрес (FakeIP локального прокси, `198.18.0.0/15`; loopback) | страница «Статус» → «Проверка доступа»; `csqtt status` | Это **не** неисправность туннеля. Проверьте реальную передачу (`curl --interface csqtt0 …`). Смена `health_target` — временный обход конкретного случая, а не универсальное исправление |
| Служба запущена, сессия установлена, но «передачи нет» | Пользовательский прокси не привязан к `csqtt0` | `csqtt status` — счётчики **↓/↑** за текущую сессию | Настройте Mihomo/ssclash на выход через `csqtt0`. Работающие воркеры и служебный обмен передачей **не** считаются |
| Web Helper «включён, но не слушает» | Порт helper занят или bind не удался (адрес вне LAN/loopback отклоняется) | страница «CAPTCHA»; `csqtt status` → `helper.running`/`helper.listen` | Освободите или смените порт. Helper слушает **только** LAN-адрес и loopback, не `0.0.0.0`/WAN |
| Служба «не запущена» после перезагрузки, хотя вчера работала | Автозапуск не включён — это **другое** состояние, чем «процесс идёт сейчас» | `ls /etc/rc.d/*csqtt*` | `/etc/init.d/csqtt enable` (автозапуск) и `/etc/init.d/csqtt start` (запуск сейчас) — разные команды |

## Команды проверки

```sh
csqtt status            # 0 подключён / 1 нет / 2 служба не запущена
csqtt doctor            # read-only диагностика (конфиг, TUN, peer, rp_filter)
csqtt doctor --json     # машинно-читаемая диагностика
csqtt log tail -n 50 -f # журнал с маскировкой секретов
logread -e csqtt        # системный лог
ip -4 addr show csqtt0  # адрес интерфейса
# пробный HTTPS-запрос именно через туннель:
curl --interface csqtt0 --max-time 15 https://1.1.1.1/cdn-cgi/trace
```

Если внешний IP в ответе совпадает с IP сервера CSQTT (а не с вашим WAN) —
трафик действительно идёт через туннель.

## Безопасная диагностика для публикации

Перед публикацией диагностики уберите секреты: `csqtt doctor --json`,
`csqtt log tail` и статус маскируют `password` и токены, но проверьте вывод
глазами — адрес сервера, `device_id` и любые вставленные вручную строки могут
оставаться. Не публикуйте ссылку `csqtt://…` и VK-токен.
