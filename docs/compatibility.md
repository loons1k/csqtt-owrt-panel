# Совместимость с прокси-клиентами

CSQTT создаёт сетевой интерфейс `csqtt0`, но сам трафик в туннель не направляет.
Направляет его **прокси-клиент**, который умеет привязывать исходящие соединения к
интерфейсу. Через туннель пойдёт только тот трафик, который клиент по своим правилам
отправит на этот интерфейс.

## Термины

- **`csqtt0`** — *сетевой интерфейс* в системе; его создаёт CSQTT. Это единственный туннель.
- **Прокси-клиент** — программа на роутере (Mihomo, SSClash, Podkop, Forkop, ZeroBlock),
  которая решает, какой трафик куда отправлять.
- **Выход** (outbound, proxy) — *элемент конфигурации клиента*, а не интерфейс. Он описывает,
  как отправлять соединения. Выход с полем `interface-name: csqtt0` означает: «отправлять
  соединения через интерфейс `csqtt0`». Отдельный TUN или второй сетевой интерфейс
  в OpenWrt для этого **не нужен** — `csqtt0` уже создан CSQTT.
- **Группа выбора** (proxy-group) — список выходов, между которыми пользователь выбирает.
- **Правила** (rules) — список «какой трафик в какой выход»; проверяются **сверху вниз**.

## Клиенты и статус проверки

| Клиент | Ядро | Выход через `csqtt0` | Особенности | Статус проверки |
|---|---|---|---|---|
| **Mihomo** | mihomo | Да: отдельный выход `type: direct` + `interface-name: csqtt0` | Маршруты, системный DNS и firewall не трогает; совместим с CSQTT | синтаксис YAML (PASS) + штатный валидатор mihomo (`-t`, v1.19.32) (PASS); **передача трафика на устройстве не проверялась** |
| **SSClash** (`luci-app-ssclash`, панель LuCI) | mihomo | Да: то же поле в конфиге mihomo | Панель редактирует конфиг mihomo напрямую; есть свой режим обработки интерфейсов | тот же механизм ядра, что у Mihomo (PASS по валидатору ядра); **на устройстве не запускался** |
| **Podkop** 0.7.23-r1 | sing-box | Да: `connection_type=vpn` + `interface csqtt0` → outbound `bind_interface` | Перехватывает системный DNS (hijack dnsmasq, FakeIP) — нужны исключения для доменов/адресов серверов CSQTT | статический анализ исходников (PASS) + синтаксис конфига sing-box (PASS); **на устройстве не запускался** |
| **Forkop** 1.0.5 | sing-box | Да: `section_interface` → `bind_interface` | Те же риски (hijack dnsmasq, FakeIP v4+v6) | статический анализ исходников (PASS) + синтаксис конфига sing-box (PASS); **на устройстве не запускался** |
| **ZeroBlock** 0.8.5-r101 | sing-box (внешний движок, закрытый генератор) | Да: `output_network_interface` (Custom Output) и outbound `bind_interface` | Перехватывает системный DNS (FakeIP, общий с Podkop/Forkop `127.0.0.42:53`); **несовместим с Podkop** — при старте сам останавливает и отключает его | статический анализ фактических пакетов 0.8.5-r101 (ipk, 24.10, `aarch64_cortex-a53`) (PASS); **на устройстве не запускался** |

Важно:

- **Наличие у клиента выбора исходящего интерфейса — не гарантия полной совместимости
  любых его версий.** Набор настроек и поведение различаются между версиями и сборками;
  проверяйте конфигурацию валидатором **своей** версии.
- Podkop и Forkop **несовместимы друг с другом** одновременно (общие `127.0.0.42:53`,
  tproxy `1602`, `rt_table 105`). ZeroBlock также делит с ними зону DNS `127.0.0.42:53` и
  **сам останавливает и отключает Podkop** — включать ZeroBlock и Podkop одновременно нельзя.
- Podkop, Forkop и ZeroBlock при совместном размещении перехватывают системный DNS и выдают
  FakeIP-адреса: резолв адресов серверов CSQTT (control-plane) может получить FakeIP →
  недоступность. Нужны исключения доменов и подсетей серверов CSQTT в настройках клиента.
- Выводы по Podkop/Forkop получены **анализом исходников и генераторов конфигов** и
  синтаксической валидацией конфигов sing-box; по ZeroBlock — **анализом фактических пакетов
  0.8.5-r101**. Работа любой из связок на реальном роутере **не проверялась**.
- SSClash — LuCI-панель над ядром mihomo: конфигурация выхода такая же, как у Mihomo.
  Документация панели: <https://github.com/zerolabnet/SSClash>.

Разделяйте уровни: возможность настройки (есть вывод через интерфейс) ≠ проверенная
конфигурация ≠ проверка на реальном устройстве. Подтверждены только возможность настройки
и синтаксис конфигурации.

## Mihomo: минимальная настройка

Официальная документация Mihomo (использованные разделы):

- общие поля прокси, включая `interface-name` — <https://wiki.metacubex.one/en/config/proxies/#interface-name>;
- выход `DIRECT` — <https://wiki.metacubex.one/en/config/proxies/direct/>;
- группа `select` — <https://wiki.metacubex.one/en/config/proxy-groups/select/>;
- правила маршрутизации — <https://wiki.metacubex.one/en/config/rules/>;
- глобальный исходящий интерфейс — <https://wiki.metacubex.one/en/config/general/#outbound-interface>.

По документации Mihomo поле `interface-name` у выхода означает: «соединения этого выхода
инициируются с указанного интерфейса». Именно это и нужно для `csqtt0`.

### Шаг 1. Добавить отдельный выход

Допишите элемент в **конец уже существующей** секции `proxies` (не создавайте вторую
секцию `proxies`):

```yaml
proxies:
  # … здесь уже есть ваши прокси …
  - name: CSQTT
    type: direct
    interface-name: csqtt0
    udp: true
```

- `type: direct` — без дополнительного прокси-протокола: соединение идёт напрямую, но
  принудительно через указанный интерфейс;
- `interface-name: csqtt0` — привязка к интерфейсу CSQTT;
- `udp: true` — можно не указывать: для типа `direct` UDP включён по умолчанию.

### Шаг 2. Включить выход в группу выбора

- Если у вас **уже есть** группа типа `select` — просто допишите строку `CSQTT` в её список
  `proxies`.
- Если группы нет — добавьте её в конец существующей секции `proxy-groups`:

```yaml
proxy-groups:
  # … здесь уже есть ваши группы …
  - name: CSQTT-Select
    type: select
    proxies:
      - CSQTT
      - DIRECT
```

Имя группы **не должно совпадать** с именем выхода: Mihomo считает это петлёй и отклоняет
конфигурацию (`loop is detected in ProxyGroup`). Имя, на которое ссылаются правила, должно
существовать, иначе проверка конфигурации не пройдёт (`proxy [...] not found`).

### Шаг 3. Добавить правила (важен порядок)

Правила Mihomo проверяются **сверху вниз, срабатывает первое подходящее**. Правило `MATCH`
подходит подо всё, поэтому всё, что стоит **ниже** `MATCH`, недостижимо (валидатор это
принимает молча — конфигурация «пройдёт», но правила не сработают).

Допишите свои строки в существующую секцию `rules` **выше** уже имеющегося завершающего
правила `MATCH`. Само `MATCH`-правило **не заменяйте и не удаляйте**: новое правило `MATCH`
в конце списка недостижимо.

```yaml
rules:
  # 1. Служебные соединения CSQTT — напрямую (выше остальных правил, см. ниже).
  - IP-CIDR,203.0.113.10/32,DIRECT,no-resolve

  # 2. Выбранный трафик — через группу с выходом CSQTT.
  - DOMAIN-SUFFIX,example.com,CSQTT-Select

  # … здесь уже есть ваши правила, включая ваше завершающее MATCH,...
  # - MATCH,DIRECT            ← СУЩЕСТВУЮЩЕЕ правило: оставьте как есть
```

`203.0.113.10` — **пример**; подставьте адрес вашего сервера CSQTT (для сервера по домену
используйте правило `DOMAIN-SUFFIX,<домен>,DIRECT`). Это правило фиксирует **прямой доступ к
серверу**: служебные соединения CSQTT к серверу должны идти через WAN, а не обратно в туннель.
Если общее правило у вас `MATCH,CSQTT-Select`, исключение для адреса сервера обязательно должно
стоять **выше** него — иначе получится петля.

### Прямой доступ нужен не только к серверу

Исключение **только** адреса сервера CSQTT закрывает не всё. Служебные соединения CSQTT идут
не только к вашему серверу, но и к **VK** (получение данных подключения и проверка) и к
**TURN** (транспорт). Эти адреса заранее неизвестны и меняются, поэтому «универсального списка
исключений» не существует и выдумывать его не нужно. Вместо этого:

- сохраните **прямой доступ** (через WAN) для служебных соединений CSQTT теми правилами,
  которые уже есть у вас, — например, отдельная группа/правило `DIRECT` для VK-доменов и
  адресов TURN, если они у вас заданы;
- либо настройте клиент так, чтобы его общее правило по умолчанию **не** направляло в `csqtt0`
  всё подряд (в первую очередь — трафик самого CSQTT).

Если служебный (control-plane) трафик CSQTT уйдёт в `csqtt0`, подключение зациклится:
ядерный трафик пойдёт в туннель, который сам не может установиться.

### Настройки самого клиента тоже влияют на маршрутизацию и DNS

CSQTT придерживается контракта **interface-only** (только интерфейс `csqtt0`, без правки WAN,
маршрутов, системного DNS/dnsmasq, firewall/NAT). Но **ваш прокси-клиент** может иметь
собственные механизмы, которые меняют маршрутизацию и DNS: перехват DNS, режим FakeIP,
свои маршруты, `rule-providers` и подобное. Такие настройки — это настройки клиента, а не
CSQTT: `csqtt0` получит трафик уже по правилам клиента, а системное разрешение имён может
возвращать синтетические адреса (FakeIP, например `198.18.0.0/15`) вместо реальных.

Практическое следствие для диагностики: активная проверка доступа CSQTT запускается **через
`csqtt0`** по системному имени; если из-за FakeIP это имя разрешилось в служебный адрес,
проверка честно помечается «не применима» (а не «туннель неисправен»). Это не заменяет
проверку реальной передачи трафика (шаг 4).

### Не используйте глобальный `interface-name`

У Mihomo есть **глобальная** настройка исходящего интерфейса
([Outbound Interface](https://wiki.metacubex.one/en/config/general/#outbound-interface)) —
это привязка **всего** трафика Mihomo к одному интерфейсу. Её не нужно задавать равной
`csqtt0`: тогда весь Mihomo, включая соединения к вашим обычным прокси-серверам, уйдёт в
туннель. Для CSQTT используется **отдельный выход** с `interface-name` (шаг 1), а не
глобальная настройка.

### Шаг 4. Выбрать выход и проверить реальный запрос

Появление выхода `CSQTT` в списке группы **не доказывает**, что трафик идёт через туннель.
Проверьте:

1. В дашборде Mihomo в группе `CSQTT-Select` выберите активным выход **`CSQTT`** (группа типа
   `select` — переключатель).
2. Сделайте реальный запрос через интерфейс `csqtt0` **на роутере**:

   ```sh
   curl --interface csqtt0 --max-time 15 https://1.1.1.1/cdn-cgi/trace
   ```

   В ответе строка `ip=` должна показывать **IP вашего сервера CSQTT**, а не обычный внешний
   IP провайдера.
3. Если дашборд показывает активные соединения — проверьте, что соединение к нужному домену
   идёт по цепочке на `CSQTT`, и что оно присутствует (правило и выход совпали).

Запрос через интерфейс `csqtt0` проверяет сам туннель. Чтобы убедиться, что **выбранный**
сайт идёт через клиент, нужен обычный запрос с устройства, трафик которого клиент
обрабатывает: во втором случае смотрите результат по внешнему IP или по активным
соединениям в дашборде.

### Если конфигурацию создаёт панель

Ядро Mihomo читает **один** YAML-файл и не имеет универсального механизма «дописать
к чужому конфигу». Если ваша панель или подписка **пересобирает файл целиком**, ручные
правки исчезнут при следующем обновлении — используйте штатный механизм панели для
пользовательских дополнений (у разных панелей он называется по-разному; смотрите
документацию **своей** панели). Например, в SSClash по его документации есть редактор
конфигурации и «Local Rulesets Management» — локальные файлы правил для `rule-providers`.

### Проверки, выполненные для этой инструкции

| Проверка | Инструмент | Результат |
|---|---|---|
| Синтаксис YAML примеров (выход, группа, правила) | PyYAML 6.0.1 | PASS |
| Конфигурация целиком — ядро Mihomo | `mihomo -t` (v1.19.32, linux-amd64), изолированная среда | PASS (`configuration file ... test is successful`) |
| Дублирование корневой секции (`proxies` дважды) | `mihomo -t` | FAIL с ошибкой `mapping key "proxies" already defined` — второй секции быть не должно |
| Ссылка правила на несуществующую группу | `mihomo -t` | FAIL: `proxy [...] not found` |
| Группа с именем, совпадающим с выходом | `mihomo -t` | FAIL: `loop is detected in ProxyGroup` |
| Правило после `MATCH` | `mihomo -t` | конфигурация принимается, но правило недостижимо — порядок обязателен |
| **Передача трафика через `csqtt0`** | — | **не проверялась** (ни роутера, ни реального сервера CSQTT) |

Проверка конфигурации **не равна** проверенной передаче трафика. Схема приведена как
соответствующая официальной документации Mihomo и проверенная валидатором его ядра; работа
на реальном роутере с реальным сервером CSQTT пока **не подтверждена**.

## Сетевой контракт CSQTT

Что именно редакция CSQTT меняет в системе роутера, а что — нет (интерфейс `csqtt0` без
правки WAN, маршрутов, системного DNS и firewall; направление трафика задаёт клиент),
подробно описано в документе [«Сетевой контракт»](network-contract.md).
